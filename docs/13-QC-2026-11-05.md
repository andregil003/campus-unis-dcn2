### 3.5 hAP-5A — FIX-02 (restos de CAPsMAN; el WiFi no emite)

El `.rsc` solo pide `configuration=cfg-wifi` (AP local). El equipo tiene, además, un `manager=capsman` y un
`datapath` heredados de fábrica:

```
/interface wifi export
/interface wifi
set [ find default-name=wifi1 ] configuration=cfg-wifi configuration.manager=capsman datapath=capdp disabled=no
/interface wifi cap
set discovery-interfaces=bridgeLocal enabled=yes slaves-datapath=capdp
/interface wifi datapath
add bridge=bridgeLocal comment=defconf disabled=no name=capdp
```

Consecuencias verificadas:

- `wifi1` está **`I` (inactive)** con el aviso `no connection to CAPsMAN` → **`UNIS-A5` no existe al aire**
  (confirmado con el escaneo: faltan `UNIS-A5` y `UNIS-B4`).
- `bridgeLocal` (defconf) sigue existiendo con `ether3` dentro, y `ether3` quedó **slave** → la regla 7 del
  firewall (`accept in-interface=ether3`) está **`I` (invalid)**: *"use master instead (bridgeLocal)"*.
- Todo lo demás está bien: `.15/32`, `10.10.5.2/30`, `10.10.6.1/30`, `192.168.5.1/24`, pool `.10‑.250`,
  DHCP `DNS=10.10.255.1`, OSPF 2 plantillas + `br-wifi`/`lo` passive, NAT vacío, 2 vecinos Full.

**Corrección (bajo riesgo, no corta el anillo):**

```
/interface wifi cap set enabled=no
/interface wifi set wifi1 !configuration.manager !datapath
/interface wifi datapath remove [find name=capdp]
/interface bridge port remove [find bridge=bridgeLocal]
/interface bridge remove [find name=bridgeLocal]
/interface ethernet set ether3 comment="hAP-5A/ether3 -> libre"
```

Si la versión rechaza el `!` (7.20.8 lo soporta), la alternativa equivalente es reaplicar el bloque 3 del
`.rsc` sobre un `wifi1` limpio. **Verificación:** `/interface wifi print` → `wifi1` sin flag `I` y
`ssid=UNIS-A5`; el escaneo del servidor debe listar `UNIS-A5`; `/ip firewall filter print` → sin reglas `I`.

**CERRADO 05/11/2026 (sesión de la tarde).** Se aplicó este procedimiento: `wifi1` sin `configuration.manager`
ni `datapath`, CAP deshabilitado, `capdp` y `bridgeLocal` eliminados y `ether3` liberado. El equipo quedó con
`wifi1` activo como AP local emitiendo `UNIS-A5`.

### 3.6 hAP-4A — PEND-01 (funciona, pero no se puede leer)

No es una falla de red: es una **falla de gestión**, y por eso no se puede certificar contra el `.rsc`.

Evidencia de que **está vivo y bien**:

- `hAP-3A` lo ve `Full` en `10.10.4.2` (`router-id=10.10.255.14`, 19h16m) y `hAP-5A` lo ve `Full` en
  `10.10.5.1` (19h15m). Es decir, **cierra el anillo Norte por los dos lados**.
- Emite `UNIS-A4`.
- Desde el servidor: `http://10.10.4.2/` → **200**; TCP 22 y 8291 **abiertos**.

Lo que falla desde el servidor (10.10.0.100):

- **ICMP: 100 % de pérdida**, incluso con 32 bytes (no es MTU: `ping -f -l 1472` a hAP-3A sí pasa).
- **SSH**: la sesión muere justo después de enviar el `KEXINIT` (`SSH2_MSG_KEXINIT sent` →
  `Connection timed out`); el servidor nunca entrega su `KEXINIT`. Es decir, el handshake se corta con
  paquetes grandes, mientras HTTP (respuestas pequeñas) sí pasa.
- `traceroute` muere después de `10.10.3.2`.

**Diagnóstico probable:** alguna regla del firewall de hAP-4A (distinta del `.rsc`) está descartando ICMP y
fragmentos/paquetes grandes. **No se puede confirmar sin leer el equipo.**

**Siguiente paso:** entrar por **WinBox a `10.10.4.2`** (puerto 8291 abierto) y hacer
`/export terse show-sensitive` + `/ip firewall filter print` + `/ip address print`. Con eso se cierra el QC
de 4A y se compara con `hAP-4A.rsc`.
