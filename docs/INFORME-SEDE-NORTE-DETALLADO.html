2. GW-A (RB5009UG+S+IN) — Configuración Completa

2.1 Qué hace GW-A

GW-A es el gateway de Sede Norte. Sus funciones principales son:

  • Salida a Internet: Tiene la WAN (ether7) hacia el router ISP del laboratorio. Toda la salida de Internet de Sede Norte sale por aquí.
  • Router-id OSPF: Su loopback 10.10.255.1 es el router-id del área 0 en Sede Norte.
  • Anuncia default por OSPF: Con originate-default=if-installed, anuncia que tiene salida a Internet, pero solo si su WAN está activa.
  • Ruta estática preferente: Tiene una ruta estática distance=1 hacia el ISP, que gana sobre OSPF (distance=110).
  • NAT: Hace masquerade hacia la WAN para que todo el tráfico de Sede Norte salga con la IP del GW.
  • DNS filtrado: Aloja el contenedor Pi-hole y fuerza todo el tráfico DNS (puerto 53) a pasar por él mediante dst-nat.
  • Contenedor: Ejecuta Pi-hole v6 en contenedor, con start-on-boot=yes.

3. hAP-1A a hAP-5A — Configuración de Cada Nodo

3.1 Qué hace cada hAP

  • Forma parte del anillo OSPF punto a punto con sus dos vecinos
  • Proporciona WiFi a los clientes con SSID UNIS-A1 a UNIS-A5
  • Actúa como gateway DHCP para los clientes WiFi
  • NO lleva ninguna regla NAT (Regla 8 del enunciado)
  • Anuncia su red WiFi por OSPF como pasiva (no forma vecinos en WiFi)

4. SXT-A (SXT Lite5) — Configuración de la Antena

4.1 Qué hace SXT-A

  • Es la punta AP (Access Point) del enlace inalámbrico inter-sede
  • No tiene IP (funciona como puente L2 transparente)
  • Se administra por MAC desde WinBox → Neighbors
  • Opera en 5 GHz con SSID UNIS-PTP
  • Se conecta con SXT-B (station-bridge) al otro lado del enlace

4.2 Configuración de SXT-A

/interface wireless set [ find default-name=wifi1 ] configuration=cfg-wifi disabled=no
/interface wifi security add authentication-types=wpa2-psk,wpa3-psk name=sec-unis
/interface wifi configuration add channel.band=5ghz-a/n .frequency=5745 .width=20mhz country=Guatemala name=cfg-wifi security=sec-unis ssid=UNIS-PTP mode=ap
/interface bridge add name=br-ptp comment="puente inalambrico inter-sede"
/interface bridge port add bridge=br-ptp interface=wifi1
/interface bridge port add bridge=br-ptp interface=ether1

4.3 Verificación en SXT-A

/interface wireless print
# Esperado: wlan1 RUNNING, modo ap-bridge, SSID UNIS-PTP, 5GHz

/interface wireless registration-table print
# Esperado: ver a SXT-B (04:F4:1C:C3:8B:F2) asociada, señal estable

/interface bridge print

Nota importante: La señal entre SXT-A y SXT-B estaba en -3 a -6 dBm (muy fuerte, casi saturación) porque las antennas están físicamente cerca (< 1 metro). Para producción se recomienda separarlas 1-2 metros o usar un atenuador coaxial 10-20 dB.

5. Pi-hole — Contenedor DNS Filtrado (Sede Norte)

5.1 Qué es y dónde corre

  • Contenedor Docker dentro de GW-A (RB5009)
  • IP del contenedor: 10.10.254.53
  • Red del contenedor: veth1 (10.10.254.0/24)
  • Estado: HEALTHY
  • Arranque automático: start-on-boot=yes
  • Root-dir persistente: /pihole6/root

5.2 Cómo funciona el filtrado DNS

  1. El cliente WiFi se conecta a UNIS-A1 (o cualquier red de Sede Norte)
  2. DHCP entrega DNS = 10.10.255.1 (loopback de GW-A)
  3. GW-A hace dst-nat del puerto 53 (UDP y TCP) hacia Pi-hole (10.10.254.53)
  4. Pi-hole bloquea dominios en su blacklist y reenvía el resto a upstreams (1.1.1.1, 9.9.9.9)

    5. 5.3 Configuración del contenedor

    /interface veth add address=10.10.254.53/24 interface=veth1 gateway=10.10.254.1 name=veth1
    /container add comment="Pi-hole DNS campus Norte" envlists=pihole_envs healthcheck-status="good, output: 127.0.0.1\\n" hostname=pihole interface=veth1 layer-dir="" logging=yes mountlists=pihole_mounts name=pihole remote-image=pihole/pihole:latest root-dir=/pihole6/root start-on-boot=yes
    /container envs add key=DNSMASQ_USER list=pihole_envs value=root
    /container envs add key=FTLCONF_dns_listeningMode list=pihole_envs value=all
    /container envs add key=FTLCONF_dns_upstreams list=pihole_envs value="1.1.1.1;9.9.9.9"
    /container envs add key=FTLCONF_misc_etc_dnsmasq_d list=pihole_envs value=true
    /container envs add key=TZ list=pihole_envs value=America/Guatemala
    /container envs add key=FTLCONF_webserver_api_password list=pihole_envs value=UNIS2026
    /container mounts add dst=/etc/pihole list=pihole_mounts src=/pihole6/etc
    /container mounts add dst=/etc/dnsmasq.d list=pihole_mounts src=/pihole6/dnsmasq.d

    7. Prueba de Failover WAN — Sede Norte

    Estado inicial (GW-A)

    /ip route print where dst-address=0.0.0.0/0
    EstadoRuta
    Normal (WAN conectada)As 0.0.0.0/0 → 100.64.1.1 (dist=1, ACTIVE)
    DAo 0.0.0.0/0 → 10.99.0.2%ether1 (dist=110, OSPF)
    WAN caídaIs 0.0.0.0/0 → 100.64.1.1 (INACTIVE)
    DAo 0.0.0.0/0 → 10.99.0.2%ether1 (ACTIVE, solo OSPF)
    RestauradaAs 0.0.0.0/0 → 100.64.1.1 (ACTIVE otra vez)

    Pasos de la prueba

    1. Desde GW-A: /ip route print where dst-address=0.0.0.0/0 — verificar que la estática es ACTIVE
    2. Desenchufar el cable de GW-A ether7 (WAN hacia ISP)
    3. Esperar 10-20 segundos
    4. Desde GW-A: /ip route print where dst-address=0.0.0.0/0 — verificar que solo queda OSPF vía 10.99.0.2
    5. Desde laptop: ping 10.20.0.100 count=3 — debe responder (tráfico cruzando inter-sede)
    6. Volver a enchufar el cable de GW-A ether7
    7. Esperar 20 segundos
    8. Desde GW-A: verificar que la estática vuelve a ACTIVE
